## 详细需求

### R3 / R16 — 帮助系统（继续讨论）

- 之前认为 Camera+ 右侧固定帮助面板更好，但维护者后续判断：**右侧帮助面板是否适合当前“左栏 + 右内容”布局仍需讨论**。
- 当前不拍板右侧面板去留，也不实施移除内联帮助。
- 继续讨论方向：
  - 帮助信息放在哪里最自然（右侧面板 / 顶部 / 底部状态栏 / 悬停 tooltip / 区块内折叠）。
  - 如何避免帮助入口破坏布局。
  - 窄屏降级方案。

### R4 / R5 / R6 — 功能块布局与导航

- 三个功能块应是三个独立、连续滚动的设置区域，而不是机械拼在同一个长滚动页。
- 每个功能块有标题，标题作为左侧导航的锚点。
- 包过滤器属于包管理块，放在包管理块内部一起滚动。
- 左侧导航切换功能块时，只显示该块的连续内容。

### R7 / R8 / R9 — Tuning Editor 交互

- Domain 多选场景使用下拉菜单。
- Action Scope 使用下拉菜单列出玩家可选项。
- Mood 因子控件做成复合控件：滑条 + 数值输入 + `−/+` 微调按钮。
- 微调按钮要有清晰的图标/视觉，不能只是看起来像文字。

### R10 / R15 — 衰减折线图作为可复用 UiKit 控件

- 当前相机高度与衰减折线图破碎、无法使用。
- 需要重做，至少达到旧 SR 的可用水平。
- 评估方向：**作为独立可复用 UiKit 控件**实现（如 `chart/line` 或 `input/range-chart`），而不是 US 一次性写死。
- 控件应支持：
  - 数据点/曲线绘制
  - 可拖拽控制点（范围起点/终点）
  - 状态/值通过 view-state 绑定
  - 中性命名，不掺 US 业务
- 建议纳入对应功能块，并随功能块一起滚动/导航。

### R11 — UiKit 容器化 + 控件基础设施（最高优先）

- 当前 UiKit `LayoutManifest` 只支持扁平根节点，需要新增容器能力（如 `Block` / `Section` / `Column`）并让 Measure/Draw/交互递归处理子节点。
- 目标是让 XML 体现结构层次：控件组合成功能块，功能块组合成更大功能块。
- 这是后续 R4/R5/R6/R7/R8/R9/R10 的公共基础，**列为最高优先**。

### R14 — 复合控件是否以容器思路呈现

- 结论：**可以，但不一定每个复合控件都要拆成 XML 子节点**。
- 建议混合策略：
  - **布局/功能块**：用容器组合（XML 层级）。
  - **紧密耦合的交互控件**（如 滑条 + 数值输入 + `−/+` 微调）：做成一个可复用的复合控件（如 `input/stepper-slider`），内部组合基础原语；不需要把每个按钮都暴露成 XML 子节点。
- 这样做的好处：
  - 复合控件可独立测试、独立复用。
  - 容器负责结构，控件负责交互，职责清晰。
  - 不会为了“纯 XML 组合”而把状态同步拆散。

## 建议实施顺序

1. **P0（最高优先）**：UiKit 容器化 + 控件基础设施（容器、复合控件、可复用图表控件）。
2. **P0**：衰减折线图作为 UiKit 控件重做。
3. **P1**：功能块独立滚动 + 标题导航 + 包过滤器归位。
4. **P1**：Tuning Editor 下拉 + Mood 复合控件。
5. **待讨论**：帮助入口方案（右侧面板是否保留继续讨论，暂不实施）。

> 具体实施前仍需维护者确认优先级与方案。
