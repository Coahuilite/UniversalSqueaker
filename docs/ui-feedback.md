# US UI 反馈记录

> 维护者/审阅者的 UI 反馈与待拍板项。当前只记录结论，不立即实施；需要维护者确认后再落地。

## 2026-08-30 — Camera+ 帮助面板方案优于当前内联帮助

- **来源**：维护者实机对比 Camera+ 设置界面后给出的反馈。
- **结论**：Camera+ 的右侧固定帮助面板方案比我们当前的内联 `?` 帮助按钮 + help banner 方案更好。
- **理由**：
  1. 玩家不需要点击帮助按钮。
  2. 玩家不需要把鼠标悬停到帮助按钮上。
  3. 不会因为展开/收起 help banner 而破坏或“弄碎”布局。
  4. 帮助信息始终固定在右侧面板，位置稳定、可扫读、可随时参考。
- **当前 US 状态**：
  - 已实现右侧帮助面板 `UsHelpPanel`（宽屏窗口总宽 ≥ 1200px 时显示）。
  - 但各区块仍保留内联 `?` 帮助按钮 + help banner，作为当前帮助入口。
- **建议方向（待拍板）**：
  - 让右侧帮助面板成为主要/唯一帮助入口，弱化或移除内联 `?` 按钮与 help banner。
  - 窄屏（无右侧帮助面板）时再考虑降级为可折叠内联帮助，避免窄屏无帮助可用。
- **状态**：待维护者确认后再动代码。

## 2026-08-30 — Camera+ 帮助机制：功能区总览 + 单项高亮独立帮助

- **来源**：维护者继续参考 Camera+ 后提出的反馈。
- **观察**：Camera+ 有一个很棒的帮助机制：
  1. 在大标题处会显式展示整个功能区的帮助（总览/说明）。
  2. 每个单独项目都有高亮指示。
  3. 每个单独项目都有独立的帮助条目。
- **当前 US 状态**：右侧帮助面板已实现，但目前只显示当前区块的一条帮助文本；没有“功能区总览 + 单项高亮 + 单项独立帮助”的分层结构。
- **建议方向（待调研）**：调研 Camera+ 的具体实现，设计 US 的“大标题总览帮助 + 单项高亮/独立帮助”机制；暂不实施。
- **状态**：已记录，晚点调研。

## 2026-08-30 — 衰减折线图破碎 + 功能块标题 + 组合式功能块思路

- **来源**：维护者审阅当前 UI 后的反馈。
- **问题 1：相机高度与衰减折线图破碎且无法使用**，甚至比旧 Squeak Ratkin 时期更糟。
  - 需要重新设计/修复该图表，目标至少达到旧 SR 的可用水平。
- **问题 2：每个功能块都应该有标题**。
  - 左侧导航应能导航到“有标题的功能块”，标题即导航锚点。
- **新思路：组合式功能块**（维护者提问“这是个好思路吗”）。
  - 控件按功能块组合；功能块可以组合成更大的功能块。
  - 示例：Action Scope + Tuning 组合成一个完整的 Tuning Editor。
  - 采用组合思路而不是一次性写死，最好在 XML 上也能看出结构层次。
- **初步评估（待确认）**：
  - 方向正确，符合当前 view-state + widget registry 的架构，也能让 XML 成为真正的结构描述。
  - 但当前 UiKit `LayoutManifest` 只支持扁平 `<Widget>` 根节点，不支持嵌套容器。
  - 要实现 XML 层级化，需要给 UiKit 增加容器/组合能力（如 `Block`/`Section`/`Column` 等），并让 Measure/Draw/交互递归处理子节点。
  - 建议分阶段：先给功能块加标题并修正包过滤器归属；再升级 UiKit 容器能力；最后把衰减图重做并纳入对应功能块。
- **状态**：待维护者确认后再动代码。

## 2026-08-30 — Tuning Editor 应继承 SR 好的交互设计

- **来源**：维护者审阅 Tuning Editor 后的反馈。
- **结论**：Tuning Editor 目前有多处交互设计不如 SR 的成熟做法，应继承 SR 的设计思路。
- **具体问题**：
  1. **多选择项应使用下拉菜单**，而不是让玩家在大量种族/异种里反复点 “Next domain >” 循环切换。
  2. **Action Scope 也应使用下拉菜单**，直接列出玩家可选项，而不是靠点击循环切换。
  3. **Mood Tuning 的 `-`/`+` 微调按钮方向很好**，但当前图标看起来是文字做的、布局也偏乱。
     - 期望：微调按钮 + 文字输入 + 滑条控件组合成“进阶滑条”——既能滑，也能微调，也能直接输入数值。
- **建议方向（待拍板）**：
  - 引入下拉选择控件（domain / scope / 其它多选场景）。
  - Mood 因子控件升级为 `滑条 + 数值输入 + −/+ 微调` 复合控件。
- **状态**：待维护者确认后再动代码。

- **来源**：维护者实机反馈。

## 2026-08-30 — 包管理筛选：race/xenotype 并列 + 选择 race 后自动筛选 xeno

- **来源**：维护者实机反馈。
- **观察**：包管理的筛选部分，或许应该把 race 和 xenotype 并列放置，下方是包列表。
- **期望交互**：玩家选择 race 后，自动筛选对应种族的 xenotype，不需要玩家手动筛选。
- **建议方向（待调研/设计）**：重构包管理筛选区为 race 列 + xenotype 列（联动），下方为语音包列表；race 选择驱动 xenotype 候选范围。
- **状态**：已记录，待处理。

## 2026-08-30 — 功能区块应独立成连续滚动区域，过滤器应属于包管理块

- **来源**：维护者审阅当前单页布局后的反馈。
- **结论**：当前三个功能块（基础设置 / 调音 / 包清单）被“机械地拼在同一个长滚动页里”，没有形成各自独立、连续可导航的设置区域。
- **具体问题**：
  - 包管理（现 UI 内称“包清单”）刚需的包过滤器，目前被放在所有设置的最顶端（Layout.xml 中 `filter-bar` 在 Basic 区块之前）。
  - 用户期望：包过滤器属于“包管理”功能块内部，而不是全局顶部。
  - 三个功能块都应各自是一个独立、连续滚动的设置区域，而不是靠顺序堆叠拼在一起。
- **建议方向（待拍板）**：
  - 每个功能块独立滚动/独立内容区；左侧导航切换块时只显示该块的连续内容。
  - 包过滤器移入包管理块内部，并跟随该块一起滚动/导航。
  - 保持“功能清晰度 > 操作效率 > 美观性”的优先级。
- **状态**：待维护者确认后再动代码。
