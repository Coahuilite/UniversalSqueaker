# UI 反馈修复前的排查工序

> 状态：建议加入实施流程。
> 背景：当前反馈存在多个“全局性风险”（G1 文本裁剪、G2 控件通路不可用、G3 下拉定位、G4 按钮视觉一致性）。这些问题根因可能跨多个 widget，直接逐个改容易漏改或重复返工，因此建议在正式修复前增加一个**系统性排查工序**。

## 1. 为什么需要排查工序

- 反馈中多个现象指向同一类根因（例如“不可用控件”已出现相机高度指示器、预设、忘记包等多个实例）。
- 若只修“当前被点名的控件”，同类问题会在其它控件继续出现。
- 部分问题需要先复现并补测试（如滚动视图内下拉定位），否则修复无法被自动门禁保护。
- 视觉类问题需要先确定“目标设计语言”，否则逐个按钮改会风格不一致。

## 2. 排查目标

输出一份可执行的问题清单，回答：

1. 哪些控件**实际不可用/不可见/不可点击**？
2. 哪些行/卡片**存在文本被裁剪**？
3. 哪些下拉**在滚动视图内定位错误**？
4. 哪些按钮/选取控件**需要统一为原版/SR 视觉语言**？

## 3. 排查步骤

### Step 1 — 交互通路排查（G2）

- 枚举所有 US widget 与 UiKit 控件中注册的 `UiInteract.Button` / `Row` / `Protect`。
- 对每个交互区检查：
  - 是否有可见绘制（表面/文字/图标）？
  - 是否可能被后续不透明 surface 覆盖？
  - 在滚动视图内命中测试是否有效？
- 特别检查：
  - 相机高度指示器
  - 相机高度预设按钮
  - 忘记包 / Forget Unavailable 按钮
  - 其它“看起来存在但点不到”的控件
- 产出：`不可用控件清单`（文件/行/原因/建议）。

### Step 2 — 下拉弹层定位排查（G3）

- 复现 Tuning Editor 中下拉展开位置错误。
- 检查 `UiInteract.RegisterPopup` / `DrawPopups` 在滚动视图内的坐标变换链路。
- 检查所有使用 `input/dropdown` 的位置：
  - Tuning Editor domain / scope
  - 包管理作者筛选（未来）
  - 其它滚动内容中的下拉
- 产出：根因结论 + 回归测试用例（“滚动视图内下拉应在触发框正下方展开”）。

### Step 3 — 文本高度排查（G1）

- 审计所有硬编码行高（如 24/26/28/30）与多行文本场景。
- 对每个卡片/行检查：
  - 标题/说明是否可能换行？
  - 绘制矩形高度是否 >= 文本测量高度？
  - 是否有 `Text.CalcHeight` / `ITextMetrics.MeasureText` 的替代？
- 特别检查：
  - BasicTuningWidget 两行内容
  - 所有 `UsCard` body 内的多行行
  - Mood 行、预设描述、帮助面板
- 产出：`文本裁剪清单` + 统一行高建议。

### Step 4 — 视觉语言排查（G4）

- 收集当前所有“切换选取项”控件：
  - 模式卡 `InputModeRowWidget`
  - Tuning layer segment
  - Action scope 下拉/按钮
  - 筛选 chip / segment
  - 快速预设按钮
- 对照：
  - 原版 RimWorld 按钮/选取控件视觉
  - SR `SqueakySettingsUI` 底部发光条 / 左侧高亮条
- 产出：`视觉替换清单`（哪些控件换成原版包装、哪些恢复 SR 高亮条）。

### Step 5 — 输出修复批次

根据排查结果把修复分成批次：

- 批次 A：全局阻断（G2 不可用控件、G3 下拉定位）
- 批次 B：可读性（G1 文本高度）
- 批次 C：视觉统一（G4 原版/SR 语言）
- 批次 D：中/低风险反馈（sticky layer、Action Scope 分组、包管理联动、黯淡显示等）

每个批次完成后跑 `verify-local.ps1` 并补回归测试。

## 4. 产出物

- `docs/ui-fix-triage-report.md`（排查结果与问题清单）——实施排查后生成。
- 每个全局风险至少一条自动化回归测试。

## 5. 是否加入

**建议加入**。理由：

- 当前反馈已经出现多个“同一根因、多点表现”的案例。
- 没有排查直接修复，容易只修表面症状。
- 排查成本远低于反复返工成本。
